2. STARTUP MIGRATION — A GENUINE PRE-'v' BOOK NOW OPENS.
   Jason's v1.0-era live book crashed the app at startup
   (the blank console): init_db's opening schema pass dies on
   a legacy index (no such column: batch_id), and the
   migration ledger then died at its credit-memo backfill
   (engine_migrations.py line 411: no such column: cm_no).
   Mechanism: the schema pass runs first and — the old book
   having no credit_memo_lines — creates that table in the
   CURRENT cm_id shape on its way to the dying index; the
   ledger's backfill then probes it by cm_no. Same artifact,
   two more tables deep: the pass also leaves an EMPTY
   current-shape ticket_lines whose FK (REFERENCES
   tickets(id)) cannot resolve against the still-number-keyed
   tickets table, and a v1.0-era book has no wo_lines at all
   for the ledger's unconditional UPDATEs. Three guards, all
   in engine_migrations.py, all in the file's own PRAGMA/DLL-
   shape idiom, all idempotent, none fabricating or dropping
   a record:

   - credit_memo_lines: when the live table is the schema
     pass's EMPTY cm_id-shaped artifact (not yet re-keyed),
     drop it and let the ledger's CREATE make the number-
     keyed shape; the existing backfill and the end-of-ledger
     re-key then run exactly as on any other pre-'v' book.
     A non-empty cm_id table is left untouched and the cm_no
     backfill is skipped (no shipped build produces one).
   - ticket_lines: the same drop-if-empty guard on the
     pass's current-shape artifact, keyed on its DDL naming
     REFERENCES tickets(id); the CREATE below then makes the
     number-keyed shape the flat-charge sync writes to.
   - wo_lines: CREATE TABLE IF NOT EXISTS in the number-
     keyed shape before the category/uom UPDATEs, same
     pattern as the ledger's other line tables.

   Proof (PHASEZ-REPORT.md carries the full outputs):

     backfilled line per memo, each carrying its memo's face
